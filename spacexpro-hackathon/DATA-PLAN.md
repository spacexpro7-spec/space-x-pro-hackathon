### Email delivery — automatic dispatch via the owner's agent loop (Gmail, owner-authorized 2026-11-06)
**Used by**: registration acknowledgments (create/join), enquiries, password-reset codes
**How it works**: Every queued email is written to `email_outbox` with a one-time `delivery_token` (migration 0003). The queuing action then calls `ctx.agent.spawnTask` (default exact-message single-flight; each dispatch carries a unique token) asking the owner's agent to send that ONE email — only that message's recipient, subject, and body — from the connected Gmail mailbox, verify the send in the mailbox's sent mail, and call `confirmEmailDelivered` with the token (and the sent message id) only after a verified send; if Gmail is not connected, the send is declined/blocked, or the send cannot be verified, the agent calls `reportEmailDeliveryBlocked` instead and the row is marked `failed` honestly. Status is never set to `sent` by the artifact itself. Organizers can re-dispatch a pending/failed row with `retryEmailDelivery` (fresh token + fresh dispatch). Dispatch failures are swallowed so registration/enquiries never fail because delivery did. No mailbox credentials are stored in the artifact or sent to the client; no bulk export takes place.
**Authorization history**: automatic dispatch shipped 2026-11-04; an audit security review removed it on 2026-11-05 because participant details + delivery token were handed to a spawned task without an owner-authorized path (queue-only hard gate, see the dated section below). On 2026-11-06 the owner explicitly authorized connecting delivery ("fix everything and connect everything like gmail acknowledgement etc etc"), so dispatch was re-wired in the minimized form above.
**Verified state (2026-11-06, checked by the builder)**: Gmail connector `status` = connected; the only account is the previous project mailbox (the delivery instructions pin that account via `accounts` + `--account`); `status --for-command +send` for that account reports `scope_status: granted` and `hatch_permission: ask` — meaning each send may present the owner an approval card; if a send is not approved/completed, the delivery agent reports it blocked and the row stays honestly pending/failed rather than sent. The public "Delivery status: pending…" banner remains removed at the owner's request; delivery status is factual in the organizer outbox.
**Processing**: Outbox rows grow only from real submissions. Reset codes are never returned to the caller; they travel only in the dispatched email body (or via the team-code recovery path).
**Acknowledgement template (2026-11-04 edit)**: The registration acknowledgement email is created and queued exactly once, at first registration only (in `registerTeam`/`joinTeam`; sign-in and portal loads never queue it). Subject is "OrbitX Hackathon — Registration Successful". The body greets the participant by name, confirms registration completed successfully, and lists participant, team name, team code, track, college, registration reference (ORB-…), payment status stated truthfully as "Pending Verification", and payment reference, followed by next steps (keep the team code safe, sign in to the Team Portal, check announcements). The same details appear on the on-screen acknowledgement. Enquiry and password-reset emails use the same professional template style; no email is ever claimed as delivered without the verified delivery-token callback.

### Artifact database (ctx.db / Drizzle + SQLite app.db)
**Used by**: all actions — settings, organizers, teams, participants, submissions, scores, announcements, enquiries, email outbox, sessions, reset tokens
**Test command**: Inspected starter `server/src/schema.ts`, `server/src/actions.ts`, and `drizzle/0001_initial.sql` in the scaffold; the runtime-provided SQLite database is the persistence layer. No separate external database connection exists in this environment, so no external DB probe was faked.
**Sample output**: Starter schema/actions compile pattern confirmed (defineAction + zod + drizzle). The existing `entries` table will be replaced by the OrbitX schema via a new migration.
**Processing**: Server-side validation on every write (team-size limits and deadlines read from settings, duplicate-email check, one-team-per-participant check, Student Innovation extra fields, role checks on every protected action). Passwords stored only as salted scrypt hashes; sessions are random tokens stored hashed/expiring in DB. Payment status stays `pending_review` until an organizer marks it verified; email rows are dispatched automatically via the agent-loop delivery pipeline and stay `pending`/`failed` until the delivery-token callback confirms a real send.

## Long-term data behavior
- **Organizer visibility (2026-11-04 edit)**: The Organizer entry point is not shown on any public page — no nav item (desktop or mobile), no footer service-status block, no footer preview toggle. The organizer area opens only for an already signed-in organizer, or via the unadvertised `#organizer` route the owner uses directly. Server-side role checks on every protected action are unchanged.
- **Refresh policy**: No scheduled refresh; data changes only through user/organizer actions. Countdown is computed client-side from stored settings dates. Email dispatch fires automatically at queue time via `ctx.agent.spawnTask`; there is no polling schedule.
- **Growth**: Teams, participants, submissions, scores, announcements, enquiries, and outbox rows grow only from form submissions and organizer actions. No seed rows of real-looking participants/teams; the only seeded row is the settings row (build-date defaults, editable by the organizer) plus a clearly labelled fictional preview dataset that lives only in client code and never touches real tables.
- **Ordering**: Teams/participants newest first in organizer lists; announcements newest first; scores ranked by weighted total descending, then earliest Round 1 submission.
- **Time semantics**: Settings dates are stored as ISO date strings in Asia/Kolkata (user timezone) and displayed as dates; created/updated instants are stored as timestamps and rendered viewer-local. Registration deadline is enforced server-side against the stored deadline date.

## Duplicate-orbits fix + premium/scroll refinement (2026-11-05 edit)
- **Diagnosed cause**: two independent orbit systems drew at different centres — the hero canvas drew 3 elliptical orbit paths with 3 planets centred at 68%/48% (desktop) or 50%/86% (narrow), while the DOM `OrbitVisual` drew 3 circular rings around its own central planet in the right column — plus a mobile-only `.hero-orbit-mobile` decoration added 2 more rings on viewports under 768px, so extra orbits appeared "sometimes" (on phones/narrow windows, and always as a doubled system on desktop). The canvas loop could also restart a second rAF chain from visibility/IntersectionObserver callbacks.
- **Fix**: a single fixed `ORBITS` configuration (exactly 3 rings) rendered once by `OrbitVisual` only; the canvas now draws stars/nebula glow/shooting stars only, with scene objects created once per mount, resize only re-sizing the backing store, and a single-loop guard (`running` flag, `cancelled` cleanup, restarts only when no chain is running). The mobile decoration JSX and its CSS were removed. No new data sources, actions, content, or imagery.
- **Premium colour refinement**: same previous palette, deepened at the edges and more luminous at centres, gentler saturation, softer glass blur with top-edge highlight/inner glow, a restrained warm-metallic accent (prize hairline, marquee hairline, growing section rules), deeper marquee gradient, and a depth veil whose opacity follows real scroll progress. Text contrast unchanged (near-white body text on deep tints). (That palette and accent have since been fully replaced by Aurora Emerald — see below.)
- **Scroll motion**: varied reveals (clip-path wipe, blur-to-sharp, slight-rotation settle, frame clip for the prize image, growing hairline rules, staggered groups), hero zoom/rise on scroll-away via `--hz` from the real scroll container, progressive nebula depth shift, counting team total, smooth FAQ accordion (grid-rows), blur-in tab switches, notice entrances, form focus glows, and button press states. All observe the host's overflow:auto scroll container; no wheel interception and no window-targeted scroll code were added, and reduced-motion disables/minimises the new motion.
